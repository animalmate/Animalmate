# 11. 장애 대응 가이드 (INCIDENT RESPONSE)

> **누구를 위한 문서인가.** 앞쪽(§1~§5)은 **회장단이 개발자 없이** 판단·조치할 수 있는 것들이다.
> 뒤쪽(§6~§8)은 **개발자 작업**이며, 여기에 손대기 전에 반드시 §0 을 읽는다.
>
> 원칙 하나만 기억하면 된다 — **네이버 카페는 글을 지우거나 고치는 API 가 없다.**
> 그래서 "다시 시도"가 위험한 유일한 영역이 발행이다. 나머지는 대체로 안전하다.

## 0. 무엇보다 먼저

| 상황 | 첫 행동 |
|---|---|
| 사이트가 아예 안 열린다 | §1 |
| 로그인/가입이 안 된다 | §2 |
| 공지가 카페에 안 올라갔다 | §3 |
| 챗봇이 답을 안 한다 | §4 |
| 메일(인증코드·알림)이 안 온다 | §5 |
| 데이터가 잘못 지워졌다 | §7 — **개발자 호출** |

**되돌릴 수 없는 것 3가지** — 하기 전에 반드시 멈추고 생각한다.
1. **카페에 나간 글** — API 로 못 지운다. 사람이 카페에서 직접 지워야 한다.
2. **회원 탈퇴 처리** — 이름·이메일·전화가 실제로 지워진다. 비활성화와 다르다.
3. **모집 기수 데이터 폐기** — 지원자 정보가 통째로 사라진다. 익명 집계만 남는다.

## 1. 사이트가 안 열린다

**먼저 확인**: <https://animalmate.vercel.app/api/health>

| 응답 | 뜻 | 조치 |
|---|---|---|
| `{"ok":true,"db":"up"}` | 서버·DB 정상 | 사이트 문제가 아니다. 본인 네트워크·브라우저를 의심한다 |
| `{"ok":false,"db":"down"}` (503) | 서버는 살아 있고 **DB 가 안 붙는다** | 아래 ⓐ |
| 아예 응답 없음 / 500 | 배포 자체가 깨졌다 | 아래 ⓑ |

**ⓐ DB 가 안 붙을 때 — 십중팔구 Supabase 일시정지다.**
무료 티어는 **7일간 요청이 없으면 프로젝트를 자동 정지**시킨다. 방학처럼 아무도 안 쓰는 기간에 일어난다.
- Supabase 대시보드 → 해당 프로젝트 → **`Restore project` / `Resume`** (1~2분)
- 정지를 막는 장치가 이미 있다: UptimeRobot 이 5분마다 `/api/health` 를 부른다(규칙 #9).
  **이 모니터를 끄면 방학 중에 서비스가 죽는다.** 껐다면 다시 켠다.

**ⓑ 배포가 깨졌을 때** — Vercel 대시보드 → Deployments 에서 직전 성공 배포를 찾아
**`Promote to Production`**(또는 `Rollback`). 코드를 고치지 않고 되돌리는 가장 빠른 길이다.
> 스키마를 바꾼 배포를 되돌릴 때는 개발자에게 알린다 — 코드만 되돌리면 DB 와 어긋날 수 있다.

## 2. 로그인·가입이 안 된다

### "가입코드가 올바르지 않습니다"가 계속 나온다
`/admin/join-codes` 를 연다(회장단).
- **"아직 발급된 코드가 없습니다"** → 활성 코드가 0개다. **아무도 가입할 수 없는 상태.** 즉시 발급한다.
- 코드가 있는데도 안 되면 **대소문자·0(숫자)와 O(알파벳)** 을 의심한다. 화면이 자동으로 대문자로 바꿔 주지만
  `0`/`O` 는 구분하지 못한다. 카페 공지에 적을 때 헷갈리는 글자가 없는 코드로 재발급하는 편이 낫다.

### "시도가 너무 잦아 잠시 막혔어요"
레이트 리밋이다. **화면이 몇 분 뒤에 다시 하라고 알려 주므로 그대로 기다리면 된다.**
- 한자리에 모여 단체로 가입해도 막히지 않도록 상한을 인원 규모에 맞춰 두었다(07-DECISIONS 73).
- 그래도 막힌다면 같은 사람이 코드를 여러 번 잘못 친 경우가 대부분이다. **정답을 넣으면 그 사람은 통과한다.**

### 인증 코드 메일이 안 온다
→ §5 로 간다.

### 특정 회원만 로그인이 풀린다
아래 중 하나가 일어난 것이다. 전부 **정상 동작**이다.
- 회장단이 그 회원을 **강등·비활성화·탈퇴** 처리했다
- 회장단이 **"모든 기기에서 로그아웃"** 을 눌렀다
- **1년 넘게 안 들어와서 멤버십이 자동 만료**됐다(§9)

## 3. 공지가 카페에 안 올라갔다

> ⚠ **먼저 카페를 눈으로 확인한다.** 글이 이미 올라가 있는데 "실패했다"고 판단해 다시 발행하면
> **같은 공지가 두 번 나가고 되돌릴 수 없다.**

`/reservations`(예약 큐)에서 그 예약의 **상태 딱지**를 본다.

| 딱지 | 뜻 | 조치 |
|---|---|---|
| **작성 중** | 필수 항목이 비어 있어 발행 대기열에 못 들어갔다 | 화면이 빠진 항목을 알려 준다. 채우면 자동으로 "업로드 대기"가 된다 |
| **업로드 대기** | 정상. 지정 시각에 나간다 | 기다린다. 시각이 지났는데도 그대로면 아래 참고 |
| **실패** | 재시도까지 했지만 못 올렸다 | 아래 「실패했을 때」 |

**시각이 지났는데 "업로드 대기"인 경우** — 발행은 pg_cron 이 **매분** 돌면서 처리하므로 보통 1분 안에 나간다.
5분 넘게 그대로면 크론이 안 돌고 있을 수 있다(§8). 여러 팀 공지가 같은 시각에 몰리면
연속 게시 방지 때문에 건마다 30초씩 벌려 나가므로 **몇 분 늦는 것은 정상**이다.

### 실패했을 때 — 원인은 화면의 실패 사유에 적혀 있다

| 사유에 보이는 말 | 원인 | 조치 |
|---|---|---|
| `봇이 쓸 수 없는 게시판` | 그 게시판의 봇 쓰기 권한이 꺼졌거나 게시판이 비활성 | `/admin/boards` 에서 확인. 카페 쪽에서 봇 계정 등급이 내려갔을 수도 있다(아래) |
| `미치환 플레이스홀더: {{...}}` | 본문의 `{{장소}}` 같은 표시를 채울 값이 없다 | 예약을 수정해 장소·정원을 채운 뒤 다시 대기로 돌린다 |
| 네이버 토큰 관련 | 봇 계정 인증이 끊겼다 | **개발자 작업** → §6 |

**중요**: 실패한 예약을 다시 대기로 돌리기 전에 **카페에 이미 글이 있는지 반드시 확인한다.**
"실패"로 기록됐어도 카페에는 올라간 경우가 이론상 가능하다(글은 올라갔는데 결과 기록 직전에 끊긴 경우).

### 봉사가 취소됐는데 공지가 이미 나갔다
카페 글은 못 지운다. 대신 예약 큐에서 **`봉사 취소 표시`** 를 누른다 —
회차가 취소로 바뀌어 **챗봇이 더 이상 그 봉사를 안내하지 않는다.** 카페 글은 사람이 지우거나 댓글로 알린다.

## 4. 챗봇이 답을 안 한다

| 증상 | 원인 | 조치 |
|---|---|---|
| "지금은 챗봇을 사용할 수 없어요" | 챗봇이 꺼져 있다 | `/admin/chatbot` 에서 켠다. **분기 한도에 도달하면 자동으로 꺼진다**(아래) |
| "오늘 사용할 수 있는 질문 수를 다 썼어요" | 그 사람의 하루 상한(기본 30회) | 정상. 다음 날 풀린다 |
| "이번 분기 챗봇 사용량이 한도에 도달했어요" | 전체 분기 한도(기본 6000회) | `/admin/chatbot` 에서 사용량 확인 후, 예산이 되면 한도를 올린다 |
| "제가 모르는 내용이에요" 만 반복 | **근거 문서가 없다** | 이건 고장이 아니다 — `/documents` 에 문서를 넣어야 답한다 |
| "질문에 주민등록번호·카드·계좌번호로 보이는 숫자가…" | 개인정보가 섞인 질문을 서버가 거절 | 정상. 그 숫자를 빼고 다시 물으면 된다 |

> 한도에 도달해 자동으로 꺼지면 **회장단에게 메일이 간다.** 조용히 죽지 않는다.

## 5. 메일이 안 온다 (인증코드·알림)

1. **스팸함을 먼저 본다.** 특히 **네이버 메일**로 자주 들어간다. 가입 화면도 그렇게 안내하고 있다.
2. 여러 명이 동시에 못 받는다면 **Gmail 일일 발송 한도(무료 ~500통/일)** 를 의심한다.
   학기초 대량 가입 때 걸릴 수 있다. 하루가 지나면 풀린다 — 급하면 나눠서 가입시킨다.
3. 한 사람이 계속 못 받으면 그 주소로 **시간당 5통** 상한에 걸렸을 수 있다. 한 시간 뒤 다시 시도한다.
4. 위가 다 아니면 공용 Gmail 의 **앱 비밀번호가 만료·회수**됐을 수 있다 → **개발자 작업**
   (Vercel 환경변수 `SMTP_PASS` 갱신).

## 6. 네이버 카페 발행이 계속 실패한다 (개발자)

**증상**: 예약이 반복해서 `failed`, 또는 `naver_tokens.status = 'error'`.

원인은 대개 둘 중 하나다.

**ⓐ refresh token 이 죽었다** — `NaverTokenError`. 봇 계정 비밀번호 변경·앱 권한 회수·장기 미사용이 원인.
```
node scripts/naver-token.mjs      # 브라우저 동의 → refresh token 재발급
node scripts/bootstrap-token.mjs  # 암호화해서 naver_tokens 에 저장(.env 값은 제거)
```
> 앱에 Callback URL `http://localhost:3000/callback` 이 등록돼 있어야 한다.

**ⓑ 봇 계정 등급이 내려갔다** — `AP003 카페스탭 등급 필요`.
실제 공지 게시판 대부분은 **카페스탭 전용**이다. 카페 매니저가 봇 계정을 **카페스탭으로 다시 임명**해야 한다.
이건 코드로 못 고친다(2026-07-23 에 실제로 겪었고, 07-24 에 임명으로 해소).

**`code 999`(연속으로 등록할 수 없습니다)는 실패가 아니다.** 워커가 대기 후 다시 시도하며
재시도 횟수도 올리지 않는다. 이 로그가 보여도 조치할 것이 없다.

## 7. 데이터를 되돌려야 한다 (개발자)

**전체 절차는 `05-ASSET-REGISTRY.md` 「백업·복원」에 있다.** 여기서는 순서만 못 박는다.

1. **먼저 멈춘다.** Supabase 에서 pg_cron 잡 2개를 `cron.unschedule` 하거나 Vercel 배포를 잠근다.
   **발행 워커가 도는 중에 DB 를 되돌리면 같은 공지가 카페에 다시 나간다.**
2. 백업 내용을 먼저 확인한다(어느 시점 데이터인지) — `node scripts/restore-backup.mjs`
3. `--to <운영 DIRECT_URL> --confirm` 으로 적용. 운영 DB 경고가 뜨고 10초 기다린다
4. `/api/health` 확인 후 크론을 다시 켠다
5. **되돌린 시점 이후 데이터는 사라진다** — 무엇이 사라졌는지 회장단에게 알린다

> **백업이 안 돌고 있으면 이슈가 자동으로 생성된다**(담당자 배정 포함). 조용히 실패하지 않는다.
> 리포에 열린 백업 실패 이슈가 있는지 가끔 본다.

## 8. 자동화(크론)가 안 돈다 (개발자)

이 서비스의 스케줄은 전부 **Supabase pg_cron → `/api/cron/*`** 이다(Vercel Cron 은 금지 — 규칙 #7).

| 잡 | 주기 | 안 돌면 생기는 일 |
|---|---|---|
| `publish` | 매분 | 예약 공지가 안 나간다 |
| `draft-generate` | 매일 | 미완성 점검 알림·미접속 만료·레이트리밋 정리가 안 된다 |
| `result-mails` | 5분 | 결과 안내 메일이 대기열에 쌓인 채 나가지 않는다(지원자는 결과가 나온 줄 모른다) |

확인:
```sql
select jobid, jobname, schedule, active from cron.job;
select * from cron.job_run_details order by start_time desc limit 20;  -- status 확인
```
- `active = false` 면 다시 켠다
- 호출은 되는데 401 이면 **`CRON_SECRET` 이 Supabase 쪽과 Vercel 쪽에서 서로 다르다.** 양쪽을 맞춘다
- 발행 워커는 **할 일이 없으면 감사 기록을 남기지 않는다**(결정 63). 로그가 없는 것이 곧 고장은 아니다 —
  `cron.job_run_details` 로 확인한다

**결과 안내 메일이 안 나갈 때**(`/api/cron/result-mails`):
```sql
select stage, status, count(*) from recruit_result_mails group by 1,2;      -- 어디서 막혔나
select stage, attempts, last_error from recruit_result_mails
 where status = 'failed' order by queued_at desc limit 20;                  -- 왜 실패했나
```
- 전부 `queued` 인데 안 줄어들면 **크론 잡이 없거나 꺼져 있다**(위 표 참조).
- `sent` 가 최근 24시간에 400건이면 **하루 한도에 걸린 것이다.** 고장이 아니라 설계대로이며,
  다음 날 이어서 나간다(결정 148). 급하면 `DAILY_CAP` 을 올리지 말고 Gmail 한도를 먼저 확인한다 —
  한도를 넘기면 **로그인 인증 메일까지 같이 막힌다.**
- `failed` 가 많고 `last_error` 에 인증·한도 문구가 보이면 SMTP 계정 쪽 문제다. 고친 뒤
  그 행들을 `status='queued', attempts=0` 으로 되돌리면 다시 시도한다.

## 9. 권한이 갑자기 없어졌다

**1년 넘게 안 들어온 계정은 멤버십이 자동으로 내려간다**(필수원칙 #2, 07-DECISIONS 82).
활동하면 저절로 갱신되므로 정상적으로 쓰는 사람에게는 일어나지 않는다.

- 되살리는 법: 회장단이 `/admin/members` 에서 역할을 다시 지정하면 된다
- 누가 언제 왜 내려갔는지는 감사 기록(`membership.expire`)에 남는다
- **마지막 회장단·시스템관리자는 이 규칙으로 내려가지 않는다.** 내리면 콘솔에서 아무도 권한을
  되돌릴 수 없기 때문에, 대신 **회장단·공용 메일로 알린다.** 그 메일을 받으면
  **지금 활동 중인 사람을 회장단으로 지정한 뒤** 쓰지 않는 계정을 정리한다.

> **만약 정말로 아무도 회장단이 아니게 되었다면** — 콘솔로는 복구할 수 없다.
> 개발자가 DB 에서 해당 회원의 `memberships.role` 을 `board` 로, `status` 를 `active` 로 되돌려야 한다.
